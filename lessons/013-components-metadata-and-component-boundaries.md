# 13. Components, metadata, and component boundaries

Angular applications are built as trees of components. A component combines a TypeScript class with metadata that tells Angular how to create it, where it can be used, what its view contains, and which styles belong to it. Understanding this boundary helps keep an application understandable as its UI grows.

This chapter introduces component anatomy and responsibility. The next chapters cover standalone template imports, selector rules, and template syntax in greater depth.

## Learning goals

After this lesson, you should be able to:

- Identify the class, decorator metadata, template, and styles that make up a component.
- Explain how Angular uses metadata to create and compose components.
- Distinguish a component from a directive and from a service.
- Choose between inline and external template or style files.
- Describe what a component boundary owns and what it should communicate.
- Recognize that style encapsulation is not a security boundary.

## 1. A component's basic parts

A component usually consists of:

1. A TypeScript class for the component's behavior and state.
2. A component decorator such as @Component with metadata.
3. A template that describes the component's rendered view.
4. Optional styles associated with that view.

Here is a small component:

~~~ts
import { Component } from '@angular/core';

@Component({
  selector: 'app-status-message',
  standalone: true,
  template: '<p class="message">The application is ready.</p>',
  styles: [
    '.message { color: darkgreen; font-weight: 600; }',
  ],
})
export class StatusMessage {}
~~~

The class is the JavaScript/TypeScript type Angular instantiates. The decorator attaches Angular configuration to it. The template and styles define the view that belongs to this component.

A component is a kind of directive that has a template. Components are used to create UI views; other directives add behavior to existing elements or change how those elements are rendered. Angular allows only one component to be instantiated for a given element in a template.

## 2. Component metadata

The object passed to @Component is component metadata. It tells Angular how to compile and use the class. Common metadata includes:

- selector: the pattern used to match this component in a template.
- template or templateUrl: the component's view markup.
- styles, styleUrl, or styleUrls: styles associated with the component.
- imports: template dependencies for a standalone component.
- providers: dependency providers scoped to the component's injector.
- encapsulation: how the component's styles are applied.
- changeDetection: the component's change-detection configuration.

A component's metadata is declarative setup. It does not replace the class: the class still contains state, methods, and other TypeScript behavior. Nor should every available metadata option be specified. Use the options that the component needs, and rely on framework defaults when they are suitable.

## 3. Inline and external view files

For a very small component, an inline template can be convenient:

~~~ts
@Component({
  selector: 'app-short-label',
  standalone: true,
  template: '<span>New</span>',
})
export class ShortLabel {}
~~~

A template can instead live in an HTML file:

~~~ts
@Component({
  selector: 'app-status-message',
  standalone: true,
  templateUrl: './status-message.html',
})
export class StatusMessage {}
~~~

The template path is resolved relative to the component's TypeScript file. Use one of template or templateUrl; do not provide both.

Styles can also be inline or stored in stylesheet files. For a short component, styles can appear in the metadata. For a larger view, separate files often make the component easier to read and edit:

~~~ts
@Component({
  selector: 'app-status-message',
  standalone: true,
  templateUrl: './status-message.html',
  styleUrl: './status-message.css',
})
export class StatusMessage {}
~~~

Use the file organization generated by the CLI and the conventions already established in the project. Angular supports both inline and external files; neither is universally required.

## 4. Components form a tree

When one component uses another component in its view, the rendered UI has a parent-child relationship. A root component contains the top-level view, and nested components can represent smaller regions or repeated kinds of UI.

For example, a page might be organized like this:

~~~text
App
└── DashboardPage
    ├── PageHeading
    ├── SummaryCard
    └── ActivityList
        └── ActivityRow
~~~

The tree describes composition, not necessarily the application's entire data model. A component should have a clear view responsibility: a page can coordinate a screen, while a smaller component can render one reusable piece.

A component boundary is useful when it gives a part of the UI a meaningful name, a focused template, or an independently understandable behavior. Splitting every element into its own component adds indirection without necessarily improving clarity.

## 5. What a component boundary owns

A component owns the view defined by its template and the styles associated with that view. It can also own the local state and behavior needed to render and operate that view.

A useful starting question is: what should a reader understand by opening this component? If its class and template mix unrelated responsibilities, consider dividing the work into focused components or services. If two small pieces always change together and have no independent meaning, keeping them together can be clearer.

A boundary is not a private sandbox for all application concerns. Components still need deliberate ways to cooperate. Parent and child components commonly exchange data and events through inputs and outputs; shared application state or business operations may belong in services. Those communication patterns receive their own lessons later in this roadmap.

## 6. A component compared with a directive or service

| Angular construct | Main role | Has its own view template? |
| --- | --- | --- |
| Component | Define and render a UI region | Yes |
| Directive | Add behavior to or change an existing element or view | No component template |
| Service | Share non-template behavior or data through dependency injection | No |

These constructs can work together. A component can inject a service, and a template can use directives. Their responsibilities differ, so choosing the right construct makes code easier to place and maintain.

## 7. Styles and the view boundary

Component styles are associated with the component view. The default emulated encapsulation scopes selectors so that component styles normally affect elements from that component's template without requiring native Shadow DOM.

Angular also supports global style behavior and native Shadow DOM encapsulation. These choices affect how CSS is applied and how DOM and styles interact. They do not make component styles a security or privacy boundary: CSS and rendered browser content are not a substitute for access control.

Global resets, typography, and design tokens often belong in application-level stylesheets. Styles for a specific component's view are usually easier to maintain alongside that component.

## 8. Standalone metadata in current Angular

Current Angular components are standalone by default. Standalone components can be composed directly by other standalone components. In Angular versions before 19, standalone did not default to true; older projects may explicitly declare components as part of an NgModule instead.

The examples in this repository use the standalone style unless a lesson is specifically explaining legacy NgModule-based code. An explicit standalone: true in a small teaching example can make its status obvious, even though current Angular does not require that setting.

How a standalone component declares its template dependencies is the subject of the next lesson, [Standalone components and template imports](014-standalone-components-and-template-imports.md).

## 9. Naming and project organization

Use names that describe the UI responsibility, such as DashboardPage, SearchBox, or ProfileCard. A component's selector is a separate template-facing name. Many Angular projects use a consistent project prefix for selectors and keep a component's class and view files together.

The exact filename convention varies between repositories and CLI versions. Follow the repository's existing style so developers can find a component's class, template, and styles without guessing.

## Common mistakes

- Treating @Component metadata as a replacement for the TypeScript class.
- Supplying both template and templateUrl, or mixing inline and file-based configuration without a reason.
- Assuming every HTML fragment needs its own component.
- Letting a page component accumulate unrelated UI and business responsibilities.
- Using a component where a directive would better add behavior to an existing element.
- Treating style encapsulation as a security boundary.
- Assuming all existing Angular projects have the same standalone defaults; older versions and NgModule-based projects differ.
- Defining component files in a way that conflicts with the workspace's generated naming conventions.

## Practical checklist

- [ ] The class has one clear UI responsibility.
- [ ] The component metadata declares the template and styles in a consistent way.
- [ ] The view is small enough to understand, or has meaningful child components.
- [ ] Component styles are placed at the scope where they belong.
- [ ] Components, directives, and services each have a clear role.
- [ ] The code follows the Angular version and file conventions used by the workspace.
