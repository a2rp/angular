# Set Up Server-Side Rendering and Hybrid Route Rendering

Angular's CLI can add server rendering support to an existing application and generate the files needed to build and serve it. After setup, server route configuration can choose client rendering, request-time server rendering, or build-time prerendering for each path.

Follow the configuration generated by the installed Angular version. Avoid replacing generated bootstrap files or server settings with a hand-written setup from a different version.

## Learning outcomes

- Add Angular SSR support to an existing project with the CLI.
- Identify the client and server bootstrap configurations.
- Configure per-route rendering modes.
- Generate static HTML for parameterized prerender routes.
- Select a fallback for paths not generated at build time.
- Build, serve, and verify the correct output for the hosting platform.

## 1. Add SSR to an existing application

Run the Angular CLI schematic in the application workspace:

~~~sh
ng add @angular/ssr
~~~

The CLI may install the SSR package, add server bootstrap files, update build and serve targets, and configure prerendering. Review the generated changes instead of assuming every workspace will get identical files.

For a new project, the CLI can scaffold rendering support with:

~~~sh
ng new my-app --ssr
~~~

Use the CLI version aligned with the Angular version already selected for the project.

## 2. Understand the generated files

A recent standalone workspace commonly includes:

- A server bootstrap entry point such as main.server.ts.
- A server application configuration such as app.config.server.ts.
- A server route configuration such as app.routes.server.ts.
- Updated Angular CLI build and serve targets.
- A generated application server or platform integration when request-time SSR is enabled.

Names and structure can differ across Angular releases and workspace styles. Treat the generated project as the source of truth.

## 3. Configure route rendering modes

A server route configuration can specify rendering behavior by path:

~~~ts
import { RenderMode, ServerRoute } from '@angular/ssr';

export const serverRoutes: ServerRoute[] = [
  {
    path: 'about',
    renderMode: RenderMode.Prerender,
  },
  {
    path: 'catalog/**',
    renderMode: RenderMode.Server,
  },
  {
    path: 'workspace/**',
    renderMode: RenderMode.Client,
  },
  {
    path: '**',
    renderMode: RenderMode.Server,
  },
];
~~~

Specific route patterns should be listed before a catch-all route. Choose the wildcard behavior deliberately; a server-rendered catch-all can make unknown paths reach your Angular app, but the app still needs correct not-found behavior.

The server configuration typically registers the routes with provideServerRendering and withRoutes. Use the generated configuration rather than duplicating providers in several files.

## 4. Prerender routes with parameters

Build-time prerendering needs a known list of parameter values. Use getPrerenderParams for a route such as articles/:slug:

~~~ts
import { inject } from '@angular/core';
import { RenderMode, ServerRoute } from '@angular/ssr';
import { ArticleCatalog } from './article-catalog';

export const serverRoutes: ServerRoute[] = [
  {
    path: 'articles/:slug',
    renderMode: RenderMode.Prerender,
    async getPrerenderParams() {
      const catalog = inject(ArticleCatalog);
      const slugs = await catalog.getPublishedSlugs();

      return slugs.map((slug) => ({ slug }));
    },
  },
];
~~~

Call inject synchronously before the first await, while the injection context is active. The data source must be available during the build and must not require an individual visitor's private session.

A route with many or frequently changing parameters can make builds slow or impractical. Choose a runtime rendering mode or a limited set of static routes when appropriate.

## 5. Choose a prerender fallback

A prerendered route can receive a request for a path that was not generated during the build. Angular supports fallback behavior such as:

- Server: render the missing path on demand.
- Client: fall back to browser rendering.
- None: do not handle an ungenerated path through a fallback.

The default fallback in current Angular documentation is Server when no fallback is specified. Set one explicitly when the product or hosting behavior needs to be clear. A static-only deployment cannot provide request-time server rendering, so its fallback and generated paths must work with static hosting.

## 6. Distinguish hybrid output from static output

A build that produces a server bundle needs a compatible runtime for routes configured as Server. Static output can generate prerendered HTML without producing an application server file. These are different deployment shapes.

If a project is intended to run entirely from static hosting, configure its output for static mode and ensure every supported path is generated or has a host-compatible fallback. If routes use request-time SSR, deploy the server output to a compatible platform.

## 7. Build and serve locally

Use the workspace's generated CLI targets:

~~~sh
ng build
ng serve
~~~

The development server helps inspect the app, but production mode and deployment behavior should also be checked. Build with the production configuration when the workspace uses one:

~~~sh
ng build --configuration production
~~~

Inspect the CLI output for prerendered paths and server/browser artifacts. Follow the generated scripts or the Angular guide to run the production server bundle for the installed version.

## 8. Verify each route directly

Do not verify SSR only by clicking links inside the already-running app. Request each route directly as a new page:

- Inspect the returned HTML for expected public content.
- Confirm prerendered routes exist in build output.
- Confirm SSR routes work in the deployed server runtime.
- Confirm client-rendered routes still bootstrap as expected.
- Check status codes, redirects, and cache headers.
- Reload after navigation and test unknown paths.

Keep user-specific data out of prerendered HTML and public shared caches. Request-time rendering does not make a response private automatically; caching and response headers must match the data.

## 9. Keep setup maintainable

- Use current CLI-generated configuration for the project's Angular version.
- Keep the server route table explicit and ordered.
- Document which routes require request-time rendering.
- Keep public static and personalized server responses on safe cache paths.
- Review generated changes during Angular upgrades.
- Deploy SSR only to a runtime supported by the platform and workspace output.

## Key takeaways

- Use ng add @angular/ssr to add the current generated setup to an existing workspace.
- Configure Client, Server, and Prerender by route using server route definitions.
- Build-time parameterized paths must be enumerable.
- Select a prerender fallback that matches the hosting model.
- Static output and request-time SSR require different deployment capabilities.
- Verify routes by direct request and inspect the actual response and build output.
