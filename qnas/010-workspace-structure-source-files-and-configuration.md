# Q&A: Workspace Structure, Source Files, and Configuration

## Workspace and project layout

### 1. What is an Angular workspace?

It is the directory managed by Angular CLI. It contains shared configuration and one or more Angular projects, along with the package and TypeScript configuration used to build and maintain them.

### 2. What is an Angular project?

A project is an application or library described in the workspace. An application can run in a browser; a library is built to be shared with other projects. Each project has a source tree and configuration.

### 3. Why can the initial app's source files be in src while its project name appears under projects in angular.json?

The angular.json projects map describes named project configuration, while the default initial application's source is commonly at the workspace root under src. The project root and sourceRoot settings explain the paths. The configuration map does not match the directory tree one-to-one.

### 4. Where do additional Angular applications and libraries usually go?

In a multi-project workspace, additional projects generated by Angular CLI are usually placed under projects/<project-name>. Each has its own source folder and project configuration.

### 5. What is the difference between src and src/app?

src contains files that support the app as a whole, such as the browser document, application entry point, global styles, and possibly assets. src/app commonly contains components, templates, styles, and other application logic. Exact structures vary with project conventions.

### 6. Why can my generated file names differ from the lesson?

Angular CLI supports different file naming styles, and defaults change between versions. Current projects may use app.ts and app.html, while others use app.component.ts and app.component.html. Follow the files actually generated by your CLI.

## Angular and TypeScript configuration

### 7. What is angular.json?

It is the workspace-level Angular CLI configuration. It describes workspace defaults and project-specific settings used by commands such as build, serve, test, and generate.

### 8. What does the projects property in angular.json contain?

It maps project names to configuration, including values such as project type, root, sourceRoot, prefix, and CLI targets. Its project entries describe settings and paths; they do not imply that an identically named folder exists at the workspace root.

### 9. What is a build target?

It is the configured task Angular CLI runs to build a project. It identifies a builder and supplies options and configurations such as entry points, assets, styles, and output settings. Builder package names and schemas vary by Angular CLI version.

### 10. What is a serve target?

It defines how the workspace starts a development server for an application. It commonly invokes a dev-server builder and refers to a build target or configuration. Inspect the generated workspace settings to see how the app is served.

### 11. What does sourceRoot mean?

It identifies the source directory for a project. The initial app commonly uses src, while an additional project may use projects/<project-name>/src. Use the configured path rather than assuming one fixed location.

### 12. How are workspace and project configuration settings combined?

Workspace-level defaults can be overridden by project-level values. Named configurations can further specialize a target, and command-line options can override settings for one invocation. Read the specific target and configuration that the command uses.

### 13. What does ng config do?

It can read or set values in the workspace's angular.json through a JSON path. You can also edit that file directly. Configuration keys in JSON use camelCase, while command-line options often use dash-case.

### 14. What belongs in package.json?

It declares packages used by the workspace and scripts that run project commands. The package manager uses it to understand dependency ranges. Check it to learn which commands the project actually defines.

### 15. What is package-lock.json for?

It records npm's concrete dependency resolution for the workspace. Keep the lockfile that matches the project's package manager and update it through that manager, rather than editing it by hand.

### 16. What is the root tsconfig.json for?

It contains shared TypeScript compiler options for the workspace. Project-specific configurations can extend it and add options for application, test, or library compilation.

### 17. What does tsconfig.app.json configure?

It supplies TypeScript and Angular compiler settings for application source. It commonly extends the root tsconfig.json. The exact options and files can vary by CLI version and project setup.

### 18. What does tsconfig.spec.json configure?

It supplies TypeScript settings for test files. Test configuration depends on the runner and project setup, so inspect the actual file rather than assuming a particular test framework.

### 19. Where do Angular template compiler options belong?

They belong under angularCompilerOptions in the relevant TypeScript configuration. General TypeScript settings belong under compilerOptions. The two sections are processed by related but distinct parts of the toolchain.

### 20. What is .gitignore for?

It tells Git which generated or local files should not be tracked. It commonly excludes node_modules and build or cache output. Do not commit installed package directories just because they appear in the workspace.

### 21. What does .editorconfig do?

It provides shared editor formatting defaults, such as indentation and line endings. It does not replace a formatter, linter, or TypeScript configuration.

### 22. What is the purpose of the generated README.md?

It documents that Angular workspace. The project README may explain how to install and run the app. The learning-notes repository README serves a separate role by organizing the course roadmap.

## Application files and assets

### 23. What is src/index.html?

It is the browser document that hosts the application. It usually contains the root selector element, such as app-root. Angular's build tool adds generated scripts and styles, so developers normally do not hardcode output bundle paths there.

### 24. What is src/main.ts?

It is the application entry point configured for the build. A standalone app commonly calls bootstrapApplication with the root component and optional application configuration.

### 25. What does app.config.ts do?

When present, it exports an ApplicationConfig passed to bootstrapApplication. It commonly registers application-wide providers, such as routing or HTTP support. Keep providers required by the app when editing it.

### 26. What does app.routes.ts do?

When generated for routing, it contains route definitions used by the router provider. Routing configuration may be organized differently in customized or older projects.

### 27. What is the difference between global and component styles?

Global styles are included for the application as a whole, often from src/styles.css. Component styles are associated with a component and are scoped according to Angular's view encapsulation behavior. A CSS file on disk is only active if the component metadata or workspace build configuration references it.

### 28. What is the public directory for?

It holds static files that are served or copied as files, such as icons and images. The build configuration determines which assets are included. Angular projects can use other configured paths, including src/assets in older or customized setups.

### 29. How do I know which asset URL to use?

Inspect the asset path configured by the workspace and the file's location. A file under public is commonly referenced from the application root URL. Other asset directories may be copied under a configured output path. Do not assume all workspaces use the same URL scheme.

### 30. Does a .spec.ts file mean the project uses one particular test runner?

No. It identifies a test-related source file convention, but the runner and builder are determined by the project setup and CLI configuration. Inspect the package scripts, test target, and configuration.

### 31. Why might an application contain server-specific files?

They are generated when server-side rendering, prerendering, or related server features are configured. A browser-only app may not have them. Do not remove them without checking which build or serve target references them.

## Inspecting and editing the workspace

### 32. How do I find which project ng build will build?

Inspect angular.json for the default project and build target, or specify a project when the command supports it. In a multi-project workspace, relying on an assumed default can build the wrong app.

### 33. Should I copy angular.json from another Angular project?

Usually not. The file depends on Angular CLI version, builders, project names, paths, and configured features. Compare the specific setting you need and adapt it to the current workspace schema.

### 34. If I add a stylesheet file, will Angular automatically use it?

Not necessarily. A component stylesheet must be referenced by that component, or a global stylesheet must be included by the configured build target. Check the component metadata and angular.json.

### 35. How do I know which config file to change?

Identify the setting and its consumer. CLI build, serve, or asset behavior is usually in angular.json; package versions and scripts are in package.json; shared TypeScript options are in tsconfig.json; template compiler options are in angularCompilerOptions; component template dependencies are in component metadata.

### 36. What should I inspect before deleting an unfamiliar file?

Search for imports or references from the entry point, component metadata, TypeScript configurations, angular.json targets, tests, and server configuration. A file can be required by a build or test target even if it is not visible in the browser UI.

### 37. Where is the authoritative documentation for the current layout?

Use Angular's file-structure and workspace-configuration guides for the version you are using. CLI-generated structure changes, so check the current docs and the configuration in your own workspace.
