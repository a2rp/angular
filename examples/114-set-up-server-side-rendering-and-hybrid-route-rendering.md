# Set Up Server-Side Rendering and Hybrid Route Rendering — Examples

This walkthrough adds Angular's generated SSR setup, assigns rendering modes to routes, and verifies the resulting build. Adapt file names and package scripts to the files generated by your Angular CLI version.

## 1. Add SSR with the Angular CLI

From the Angular project root:

~~~sh
ng add @angular/ssr
~~~

Review the changes to package.json, angular.json, and the generated server bootstrap and configuration files. Keep the versions aligned with the rest of the Angular workspace.

## 2. Configure known routes

Example app.routes.server.ts:

~~~ts
import { RenderMode, ServerRoute } from '@angular/ssr';

export const serverRoutes: ServerRoute[] = [
  {
    path: 'about',
    renderMode: RenderMode.Prerender,
  },
  {
    path: 'articles/:slug',
    renderMode: RenderMode.Prerender,
    async getPrerenderParams() {
      const catalog = inject(ArticleCatalog);
      const slugs = await catalog.getPublishedSlugs();

      return slugs.map((slug) => ({ slug }));
    },
    fallback: PrerenderFallback.Server,
  },
  {
    path: 'search',
    renderMode: RenderMode.Server,
  },
  {
    path: 'workspace/**',
    renderMode: RenderMode.Client,
  },
  {
    path: '**',
    renderMode: RenderMode.Server,
  },
];
~~~

Complete the imports used by the parameterized route:

~~~ts
import { inject } from '@angular/core';
import { PrerenderFallback, RenderMode, ServerRoute } from '@angular/ssr';
import { ArticleCatalog } from './article-catalog';
~~~

Combine the snippets into one file and remove duplicate imports. The service must be available at build time and return only public slugs. Call inject before awaiting. The server fallback allows an ungenerated slug to be handled at request time, so the production deployment must provide a compatible SSR runtime.

The final wildcard is only an example. Review not-found behavior and place more specific paths before the catch-all route.

## 3. Register the server route table

The generated server application configuration typically includes a provider like:

~~~ts
import { ApplicationConfig } from '@angular/core';
import { provideServerRendering, withRoutes } from '@angular/ssr';
import { serverRoutes } from './app.routes.server';

export const serverConfig: ApplicationConfig = {
  providers: [
    provideServerRendering(withRoutes(serverRoutes)),
  ],
};
~~~

Keep generated providers and server bootstrap parameters that your workspace requires. Do not copy this small fragment over the full generated file.

## 4. Set response metadata for a server-rendered route

A server route can specify a status or response headers:

~~~ts
{
  path: 'search',
  renderMode: RenderMode.Server,
  status: 200,
  headers: {
    'Cache-Control': 'public, max-age=60',
  },
}
~~~

Use cache directives that match the data. Public, shared output may be cacheable. For personalized content, use a private or no-store policy as appropriate and verify the final headers from the deployed server.

## 5. Configure a static-only deployment

If the application must run without an Angular rendering server, configure the build target for static output in angular.json:

~~~json
{
  "projects": {
    "my-app": {
      "architect": {
        "build": {
          "options": {
            "outputMode": "static"
          }
        }
      }
    }
  }
}
~~~

This is a partial configuration. Merge it into the existing build options and ensure the selected routes can be generated or served by the static host. Do not leave routes that require request-time server rendering in a static-only deployment.

## 6. Build and inspect generated output

Run the project's build:

~~~sh
ng build --configuration production
~~~

Inspect the output and build messages for:

- The prerendered about page.
- One HTML page for every slug returned by the catalog service.
- Browser and server output, if the project uses request-time SSR.
- Warnings about routes that could not be prerendered.

Build behavior and output directories can vary by Angular builder and project configuration.

## 7. Verify direct requests

With the app running on a local or deployed server, request routes directly:

~~~sh
curl.exe -i https://example.test/about
curl.exe -i https://example.test/articles/angular-basics
curl.exe -i https://example.test/search?q=signals
curl.exe -i https://example.test/workspace
~~~

Replace the host and routes with the application URLs. Check status, cache headers, and returned HTML. For an article, try both a generated slug and an ungenerated slug to confirm the configured fallback. A static host should instead serve generated paths or follow its documented client fallback rules.

Then open the same routes in a browser and verify the client application starts and interactions work. Chapter 115 covers hydration behavior.

## 8. Keep the runtime patched and trusted

SSR adds server request handling. Keep Angular packages on supported security patches, and deploy behind a correctly configured proxy. Treat forwarded host and protocol headers according to the platform's trusted-proxy configuration. Do not construct absolute URLs or cache keys from unvalidated request headers in custom server code.
